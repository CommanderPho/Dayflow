# Dayflow Sync — проекты, несколько компьютеров, команды

Описание сервера синхронизации Dayflow (`server/`), приложения Dayflow для Windows (`windows/`) и веб-дашборда (`server/web/`).

- **Часть 1** — функциональное описание: что умеет система с точки зрения пользователя.
- **Часть 2** — техническая реализация на стороне сервера.

Сервер: `http://192.168.0.90:8790` (megaserv, Docker, compose-проект `dayflow`). Контракт API: `docs/sync-server-design.md`.

---

# Часть 1. Функциональное описание

## Кто есть кто

| Роль | Кто это | Что может |
|---|---|---|
| **Пользователь** | Любой, кто вошёл через Google | Свои данные со всех компьютеров, свои настройки публикации |
| **Viewer** | Участник пространства «только смотреть» | Ленты, отчёты и стендапы проектов |
| **Member** | Обычный сотрудник | Как viewer, плюс привязывает свою работу к проектам и отправляет свои таймшиты |
| **Admin** | Руководитель или менеджер | Плюс создаёт и настраивает проекты, приглашает людей, меняет роли, подключает Odoo |
| **Owner** | Владелец пространства | Всё, включая назначение других owner/admin |

Рабочее пространство — это компания или команда. Первое пространство создаётся автоматически при первом входе адреса, указанного администратором сервера (`BOOTSTRAP_ADMIN_EMAILS`).

## 1. Один человек, несколько компьютеров

**Подключение компьютера:**
1. В Dayflow: Настройки → «Sync & team» → **Войти через Google**.
2. Откроется браузер, нужно войти в аккаунт. Компьютер появится в списке устройств.
3. После первого входа на сервер уходят карточки за последние 30 дней.

**Что получает пользователь:**
- **Общий таймлайн.** На любом компьютере виден весь день, в том числе то, что делалось на других машинах. Чужие карточки показываются отдельной дорожкой с названием устройства.
- **Правки везде.** Переименовали карточку, сменили категорию, удалили, пометили приватной на одном компьютере — изменение появится на остальных через несколько секунд. Правки с разных машин не затирают друг друга.
- **Общие настройки и итоги.** Категории, стендапы и цели дня одинаковые на всех компьютерах.
- **Работа без сети.** Без связи с сервером Dayflow работает как обычно, а изменения догоняют сервер, когда связь появится.
- **Веб-дашборд.** Кнопка «Open web dashboard» открывает в браузере тот же день и неделю по всем устройствам, вход выполняется автоматически.

**Что не синхронизируется никогда:** скриншоты, таймлапсы, accessibility-лог, история чата с ИИ. Они остаются на компьютере, где записаны.

**Управление устройствами:**
- В списке устройств любое можно **отозвать**, например потерянный ноутбук. Он сразу перестаёт синхронизироваться.
- **Выход** на компьютере отзывает его и убирает с него чужие карточки и проекты. Собственные записи этого компьютера остаются.

## 2. Проекты

Проект — это то, на что тратится время: клиент, продукт, задача. Его создаёт admin в приложении или в дашборде.

**Настройки проекта:**
- **Название, цвет, описание.** Описание помогает ИИ понимать, что относится к проекту.
- **Правила автопривязки:**
  - программы, например `code`;
  - сайты, например `odoo.com`;
  - ключевые слова в заголовках, например «Biosun»;
  - репозитории, например `dayflow`.
- **Уровень публикации по умолчанию** (см. раздел 4).
- **Связка с Odoo:** проект и задача в Odoo, куда пойдут таймшиты.
- **Архив:** проект скрывается из списков, история остаётся.

**Как работа попадает в проект:**
1. **Вручную.** В карточке выбирается проект, можно несколько с долями, например 70% Biosun и 30% Dayflow.
2. **По правилам.** Карточка привязывается сама, если сработало правило проекта.
3. **Через ИИ.** При разборе дня ИИ сам предлагает проект. Уверенная догадка принимается сразу, неуверенная показывается на карточке чипом «?». Клик по чипу подтверждает её, или можно выбрать другой проект.

В таймлайне есть фильтр по проекту.

## 3. Команда

**Пригласить коллегу:**
1. Admin открывает дашборд → проект или пространство → Members → вводит email и роль.
2. Получает ссылку и отправляет её коллеге.
3. Коллега ставит Dayflow, входит через Google **под тем же email**, открывает ссылку и вступает.
4. Проекты пространства сразу появляются в его приложении.

**Что видит команда в проекте** (вкладка Team в приложении и страницы проекта в дашборде):
- **Лента:** кто, когда и сколько работал над проектом по дням. Подробность зависит от уровня публикации каждого участника.
- **Отчёт:** итого часов, разбивка по людям и по дням, тепловая сетка «человек × день», категории работ.
- **Стендап проекта:** по каждому участнику — время за день и пункты «сделано / дальше», относящиеся к проекту.
- **Диапазоны:** день, неделя, месяц или свой период.

**Отчёт по команде** (дашборд → Team, только admin и owner):
- **Люди:** каждый участник пространства, в том числе без времени за период. Итого часов, разбивка по проектам с долями, активные дни, среднее за день, часы, отправленные в Odoo, когда последний раз синхронизировалось его устройство.
- **Проекты — кто сколько внёс:** итого по проекту, доля проекта во всём времени, вклад каждого человека в процентах.
- **Матрица «человек × проект»:** часы и доля человека в проекте; ниже — часы по дням и сетка «человек × день».
- **Export CSV:** строки «человек × проект» с часами и долей, затем итоги по людям (разделитель `;`, десятичная запятая — открывается в Excel).
- В отчёте та же проекция, что и в отчётах проектов: только подтверждённая проектная работа. Приватные карточки, неподтверждённые догадки ИИ и время вне проектов в него не попадают.

В отчёте проекта (вкладка Report) у каждого участника рядом с часами показана его доля в проекте.

**Пользователи** (дашборд → Users, только admin и owner):
- Список всех участников за выбранный период: сколько времени записали их компьютеры (Tracked: проектная работа плюс блоки «Out of scope»), сколько из этого подтверждённая проектная работа и её доля, число дней.
- У каждого человека — его компьютеры: время каждой машины за период и когда она последний раз синхронизировалась. Отозванные машины показываются, только если у них есть время в периоде.
- Поиск по имени и e-mail. Клик по человеку открывает его таймлайн, клик по компьютеру — таймлайн только этой машины.
- Если два компьютера человека записывали одновременно, в Tracked учитываются оба. Работа, подтверждённая только для проектов другого пространства, не учитывается.
- Для admin строки owner'ов показываются без собственного времени и без перехода в таймлайн; проектное время owner'а видно, как и в отчётах проектов.

**Таймлайн человека и его машин** (дашборд → Users → человек или компьютер; из Team — кнопка Timeline):
- День или неделя, по дорожке на каждый компьютер человека; фильтр «All devices / конкретная машина». Сверху список его устройств и когда каждое последний раз синхронизировалось.
- Проектная работа показана с уровнем публикации человека: «Только время» — блок с именем проекта, «Карточки» — название и описание, «Подробно» — плюс хронология и отвлечения.
- Остальное время — блоки «Out of scope» без описания. Личное и приватное на сервер не попадает, поэтому его здесь нет.
- Тот же фильтр по машинам появился и в «My time».

## 4. Приватность: каждый решает сам

Главный принцип: **команда видит только то, что человек подтвердил как работу над проектом, и ровно с той подробностью, которую он выбрал.**

| Уровень | Что видят коллеги |
|---|---|
| **Только время** | «Иван, 2 ч 15 мин, вторник», без названий и описаний |
| **Карточки** | плюс название и краткое описание работы |
| **Подробно** | плюс подробная хронология и отвлечения |

- У проекта есть уровень по умолчанию (его задаёт admin), но **каждый участник может поменять свой уровень** в этом проекте.
- **Неподтверждённые** догадки ИИ команде не видны, пока человек их не подтвердит.
- Карточка с пометкой **«приватно»** никогда не попадает в командные отчёты, даже если привязана к проекту.
- Работа вне проектов (отвлечения, другие проекты) коллегам **не видна**. Admin и owner видят её в таймлайне человека только как время без описания («Out of scope»).
- Личные карточки (категория Personal и другие исключённые) и карточки с пометкой «приватно» **не покидают компьютер**. Их не видит никто, включая admin и owner.
- **Admin и owner видят таймлайн каждого участника** по всем его машинам (дашборд → Users → человек): когда и на каком компьютере шла работа. Проектные карточки показаны с тем уровнем публикации, который человек выбрал для проекта, всё остальное — только время.
- Работа, подтверждённая только для проектов **другого** пространства, в таймлайне и во времени этого пространства не показывается.
- Admin не видит таймлайн и собственное время owner'а; owner видит всех.
- **Каждый просмотр чужого таймлайна записывается.** Человек видит на странице Account в дашборде, кто, когда и за какой период открывал его таймлайн.
- Человек, вышедший из пространства, исчезает из его отчётов.

## 5. Таймшиты в Odoo

**Один раз настраивает admin** (дашборд → Workspace settings → Odoo):
1. Адрес Odoo, база, логин, API-ключ → «Test connection».
2. Сопоставление людей с сотрудниками Odoo (`hr.employee`). Есть кнопка «Match by e-mail».
3. В каждом проекте указывается проект или задача Odoo.

**Дальше каждый сотрудник** (приложение → Team → Timesheets или дашборд → Timesheets):
1. Выбирает период и видит предложенные строки «день × проект». Часы округлены до 0,25 и взяты только из подтверждённой работы, описание собрано из названий карточек.
2. Правит часы и описание, отмечает нужные строки.
3. Нажимает **Submit**. Окно подтверждения перечисляет ровно то, что будет записано в Odoo.
4. После подтверждения строки создаются в Odoo. По каждой строке показывается результат.
5. Повторная отправка того же дня и проекта **обновляет** строку, а не создаёт дубль. Такие строки помечены «Existing in Odoo #id».

Без нажатия Submit система в Odoo ничего не пишет.

## 6. Типичный день

1. Сотрудник работает утром на десктопе, днём на ноутбуке. Dayflow на обоих сам собирает день, и вечером на любом из них виден весь день.
2. Вечером он пробегает таймлайн: подтверждает «?» на паре карточек, одну личную помечает приватной.
3. Руководитель утром открывает проект в дашборде: часы команды за вчера, лента по уровням публикации, стендап проекта.
4. В пятницу сотрудник открывает Timesheets, проверяет неделю и отправляет её в Odoo.

## 7. Текущие ограничения

- **Все проекты пространства видны всем его участникам.** Закрыть проект от части коллег нельзя. Пока что выход — разделить людей по разным пространствам.
- **Стендап проекта отбирает пункты из личного стендапа по совпадению слов** (название проекта, ключевые слова). Посторонний пункт с таким словом может туда попасть. При уровне «только время» текст стендапа не показывается совсем.
- **Сервер доступен только из сети компании** (LSZ и площадки через WireGuard). Для работы из дома нужен VPN или публикация на домене.
- **Вход работает только после создания Google OAuth client** (тип Desktop app) и записи его ID и Secret в `/srv/dayflow/.env`.

# Часть 2. Техническая реализация (сервер)

Код: `server/src`, схема БД: `server/migrations/001_init.sql`.

## Общая модель

Сервер — это реле и агрегатор результатов. Анализ экрана идёт только на компьютерах; на сервер попадают карточки, наблюдения, стендапы, цели, категории и привязки к проектам. Скриншоты и accessibility-лог на сервер не попадают.

Все синхронизируемые таблицы устроены одинаково:
- `id`: uuid или составной ключ;
- `user_id`: владелец записи;
- `device_id`: какое устройство записало;
- `hlc`: гибридные логические часы вида `<мс, 13 цифр>-<счётчик hex>-<deviceId>`, сравниваются как строки;
- `deleted`: мягкое удаление;
- `server_seq`: номер из одной глобальной последовательности `sync_seq`, по нему считаются курсоры pull.

## Мульти-станции (один пользователь, много ПК)

**Устройства и вход** (`auth/auth.ts`, таблица `devices`):
- Вход через Google (десктопный OAuth: loopback + PKCE). Сервер сам меняет code на токены, проверяет ID-токен и `email_verified`, затем регистрирует устройство.
- Каждое устройство получает свой токен `dfd_…`. В базе хранится только его SHA-256, токен можно отозвать (`revoked_at`).
- Если клиент предложил свой uuid устройства и он свободен, сервер его принимает. Если это уже живое устройство того же пользователя, сервер выдаёт новый токен на тот же id. Поэтому локальные записи сохраняют свой `device_id`.
- Веб-сессия: устройство запрашивает одноразовый код на 60 секунд, по нему ставится HttpOnly cookie с JWT на 12 часов.

**Push** (`sync/engine.ts → push`):
- До 1000 изменений за запрос.
- Предпроверка без обращения к БД:
  - `deviceId` изменения должен совпадать с устройством токена (`foreign_device`);
  - HLC должен быть корректным и не уходить в будущее больше чем на 5 минут;
  - deviceId внутри HLC должен совпадать с устройством;
  - `fieldHlc` разрешён только у карточек.
- Изменения применяются в порядке «родитель → потомок»: project → project_member → card → card_project → остальное.
- Всё идёт одной транзакцией, но у каждого изменения свой SAVEPOINT. Одно отклонённое изменение не роняет пачку: оно попадает в `rejected` с причиной.
- Чужие записи отклоняются (`not_owner`), если `user_id` записи не совпадает с вызывающим.

**Слияние карточек.** Это главная часть.
- **Поля анализа** (время, summary, detailed, metadata, is_error) может менять только устройство-генератор (`cards.device_id`). Правило: запись целиком, побеждает последний HLC (`analysis_hlc`).
- **Пользовательские поля** (`title`, `category`, `subcategory`, `deleted`, `private`) сливаются отдельно, по последнему HLC каждого поля (`field_hlc`):
  - явная правка с `fieldHlc` побеждает, если её часы новее;
  - переанализ на генераторе меняет поле, только пока его никто не правил вручную;
  - устройство-не-генератор без `fieldHlc` с отличающимся значением считается ручной правкой.

  Итог: переименование на ноутбуке и смена категории на десктопе сохраняются обе, а следующий переанализ на десктопе их не затирает.
- Остальные сущности (card_project, observation, standup, day_goal, user_doc) сливаются по принципу «последняя запись побеждает», через `lwwGuard`.

**Pull и уведомления:**
- `GET /api/sync/pull?cursor=` выбирает из 8 источников строки с `server_seq > cursor`. Каждый источник отдаёт до n+1 строк, результаты сливаются по seq; ответ содержит `more` и новый `cursor`.
- Пользователь получает все свои записи со всех устройств, свои же записи клиент отфильтровывает сам. Плюс проекты и участников всех рабочих пространств, где он состоит.
- `GET /api/sync/stream` (SSE) шлёт только сигнал `changed` (данные клиент затем забирает через pull). `feed` — для обновлений ленты проекта, `ping` — каждые 25 секунд. Рассылка внутри одного процесса (`sync/hub.ts`), без внешнего брокера.
- Сводный таймлайн для дашборда: `GET /api/me/timeline` отдаёт карточки со всех устройств пользователя, дорожки по устройствам строит UI.

## Мульти-юзеры (команды)

**Рабочие пространства и роли** (`workspaces`, `memberships`, `access.ts`):
- Роли упорядочены: viewer < member < admin < owner.
- `requireWorkspaceRole` и `requireProjectRole` возвращают 404 не-участнику (чтобы не раскрывать, что ресурс существует) и 403, если роль недостаточна.
- Первый вход адреса из `BOOTSTRAP_ADMIN_EMAILS` создаёт пространство по умолчанию и делает этого пользователя owner.
- Приглашение: admin создаёт его на email и роль; токен хранится хэшем и имеет срок. Принять приглашение может только пользователь с тем же email.
- При вступлении нового участника `touchWorkspace` заново проставляет `server_seq` проектам пространства. Курсоры устройств новичка уже ушли дальше, а так они всё равно получат все существующие проекты.

**Что и кто может писать:**
- Проекты: admin и owner. Это проверяется и в push, и в REST.
- Свой уровень публикации в проекте (`project_members`): сам участник или admin.
- Привязку `card_project` — только владелец карточки, и только к проекту пространства, где он хотя бы member.
- Чужие наблюдения и документы недоступны никому, включая owner пространства. Команда видит только проекцию.
- Чужие карточки admin и owner видят только через `GET /api/workspaces/:id/members/:userId/timeline`: участник этого пространства, все его устройства, без приватных, удалённых и ошибочных карточек и без работы, подтверждённой только для проектов других пространств. Admin не может открыть таймлайн owner'а (403). Каждый просмотр чужого таймлайна пишется в `timeline_views` (повтор того же периода тем же человеком в течение 10 минут не дублируется), список — `GET /api/me/timeline-views`. Содержимое урезается на сервере: у карточки, подтверждённой для проектов этого пространства, — по самому низкому уровню публикации среди этих проектов (`time` — вместо названия имена проектов, без описаний; `cards` — название, summary, категория; `detailed` — плюс подробное описание и отвлечения). Остальные карточки отдаются как «Out of scope» без текста. Сайты и приложения (`appSites`) не отдаются никогда; из категорий пользователя — только названия и цвета.

## Проектность

**Сущности:**
- `projects`:
  - пространство, название, цвет, описание;
  - `rules` (apps, domains, titleKeywords, repos);
  - `default_share` (time | cards | detailed);
  - связка с Odoo (`odoo`: projectId и taskId);
  - флаг `archived`.
- `card_projects`: привязка карточки к проекту:
  - `share` — доля от 0 до 1 (одна карточка может делиться между проектами);
  - `source` — manual | rule | llm;
  - `confidence` — уверенность;
  - `confirmed` — подтверждена ли.

Привязку вычисляет клиент: вручную, по правилам или через LLM. Неуверенная LLM-привязка помечается `confirmed=false`. Сервер её только хранит.

**Проекция для команды** (`sync/projection.ts → project_entries`). Это единственное место, где личные карточки становятся видны другим людям. Она пересчитывается внутри той же транзакции push, затронутые карточки и проекты собираются в `Effects`.
- **Какие привязки попадают:** только подтверждённые и не удалённые. Карточка не удалена, не ошибка, не приватная. Проект не удалён. Владелец карточки состоит в пространстве проекта (вышел — его записи исчезают при пересчёте).
- **Уровень публикации:** `project_members.share_level`, а если он не задан — `projects.default_share`:

| Уровень | Что видит команда |
|---|---|
| `time` | день и минуты |
| `cards` | плюс title, summary, category |
| `detailed` | плюс detailed summary и distractions |

- **Минуты:** длительность × share. Если сумма подтверждённых долей одной карточки больше 1, доли пропорционально уменьшаются, чтобы время не задвоилось.

**Командные представления** (`routes/team.ts`, нужна роль хотя бы viewer):
- `feed`: записи `project_entries` за период.
- `report`: итоги по участникам, дням, участникам × дням и категориям.
- `users` (`GET /api/workspaces/:id/users`, роль admin): участники с устройствами; минуты карточек (без приватных, удалённых, ошибочных) по каждому устройству, проектные минуты из `project_entries`, число дней.
- `workspace report` (`GET /api/workspaces/:id/report`, роль admin): все участники пространства с итогами из `project_entries` по проектам не удалённым, часы `timesheet_exports` со статусом `sent`, последний `last_seen_at` неотозванных устройств; суммы «человек × проект», «человек × день», по дням.
- `standup`: по каждому участнику — минуты за день. При уровне не ниже `cards` к ним добавляются пункты его личного стендапа, но только те, что совпадают с названием проекта, его ключевыми словами или заголовками его записей в проекте. При уровне `time` текст стендапа не показывается совсем.

**Таймшиты Odoo** (`odoo/timesheets.ts`):
- **Предложение:** сумма подтверждённых минут пользователя по (день, проект), округлённая до 0,25 ч.
- **Отправка:** только по явному submit, через XML-RPC `account.analytic.line`.
- **Идемпотентность:** ключ `(user, day, project, task)` с UNIQUE в `timesheet_exports`. Повторная отправка обновляет (`write`) уже созданную строку, а не создаёт новую.
- API-ключ Odoo хранится зашифрованным; пользователи сопоставляются с `hr.employee` через `employee_map`.

## Технические ограничения

1. **Доступа на уровне проекта нет.** Любой участник пространства (даже viewer) видит ленту и отчёт любого проекта этого пространства. `project_members` сейчас задаёт только уровень публикации. Если нужны закрытые проекты внутри одного пространства, понадобится отдельная ACL.
2. **Проектный стендап отбирает пункты по совпадению слов.** Пункт личного стендапа, случайно содержащий название проекта или его ключевое слово, попадёт в стендап проекта. При уровне `time` такого не бывает.
3. **Сервер читает личные данные.** Это нужно для проекции и дашборда; данные зашифрованы только на уровне тома Postgres. Сквозного шифрования нет.
4. **Только один экземпляр сервера.** SSE работает внутри процесса, поэтому горизонтально масштабировать нельзя без брокера (например, Postgres LISTEN/NOTIFY или Redis). Для одной компании этого хватает с запасом.
5. **Проекция пересчитывается синхронно внутри push.** На больших пачках это даёт задержку, зато отчёт никогда не отстаёт от данных.
